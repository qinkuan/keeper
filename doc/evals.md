# 效果评估闭环（Evals）

> 本文描述**已实现**的评测闭环。落点：`keeper/evals/`（spec / asserts / harness /
> runner / report / run）、产物目录 `~/.keeper/evals/`。

---

## 一、一句话

用**固定的普通聊天用例**跑 agent，用**程序化断言**判定结果，
产出**可 diff 的基线**，让「改了之后变好还是变坏」有据可依。

---

## 二、为什么不依赖「agent 定位」

评测不假定 agent 是什么角色、有什么能力。用例是**普通聊天**：

```
问题：把这个函数改成支持批量输入
断言：工作区里出现了改动后的文件 / 输出里包含某些关键词 / 步数没超上限
```

好处：换 agent、换模型、换插件都能用同一套用例跑，结果可比。

---

## 三、三层判定（刻意只做前两层）

| 层 | 判定什么 | 怎么做 |
|---|---|---|
| **L1 能不能干完** | 任务是否完成 | 程序化断言 |
| **L2 干得好不好** | 过程指标（步数、token、成本、耗时） | 从 `llm_calls` 聚合 |
| L3 干得对不对 | 语义正确性 | **不做** |

L3 不做，因为要引入 LLM judge，而 judge 换个模型 / 换个提示词评分口径就变了，
历史基线全部作废。评测最怕的就是**口径会漂**——漂了就无法比较。

### 3.1 断言是纯程序化的

`evals/asserts.py`：不引入第二个模型。

断言类型大致包括：文件是否存在 / 内容是否含某串 / 步数上限 / token 上限 /
是否调用了某工具 / 是否产生了某产物。

---

## 四、隔离：三重（其中一条是可验证的断言）

评测最怕**污染真实数据**和**跑不起来**：

| 隔离 | 做法 |
|---|---|
| **独立数据库** | 用 SQLite backup API 把真实库复制一份到运行目录 |
| **独立进程** | 评测在独立进程里跑，不干扰主服务 |
| **独立工作空间** | 用临时目录，不与用户工作区混 |

**进程隔离是前提，不是可选项**：agent 会写文件、会连 MCP，跑在主进程里一旦出错
影响的就不只是评测。

其中「独立数据库」是可验证的断言——评测结束后真实库应当**未被修改**。

---

## 五、配置指纹

没有配置指纹，基线就是一堆孤立数字：换了个模型、换了个插件，数字变了，
但你不知道是「改好了」还是「配置变了」。

所以每条基线记录当次运行的配置指纹（模型、插件、关键参数），
对比时**先比指纹**，指纹不同就直接提示「不可比」。

---

## 六、用例规格（`evals/spec.py`）

一条用例 = 一个问题 + 一份断言 + 若干准备条件。

刻意做得很薄：**只支持「确定性准备」**，不支持预置记忆 / 预置历史——
那两样要么依赖记忆抽取（模型侧，不稳定），要么让用例变成另一个要维护的系统。

用例文件 YAML，当前自带 `cases/smoke.yaml`（冒烟集）。

---

## 七、执行（`evals/runner.py`）

三条编排取舍：

1. **串行跑用例** —— 评测烧的是真钱（每条一次完整 ReAct），并发只会让失败率
   上升，不利于定位
2. **逐条判定后继续** —— 一条失败不影响其他条
3. **过程指标从 `llm_calls` 取** —— 与可观测同源，不另建统计

命令行：

```bash
# 跑默认 smoke 用例集（自动选库里第一个 active agent）
python -m keeper.evals.run
```

---

## 八、报告（`evals/report.py`）

两层产物，职责不同：

| 产物 | 用途 |
|---|---|
| `baselines/<run_id>.json` | **唯一真相源**：机器读、前端读、对比读 |
| `baselines/<run_id>.md` | 人看的 Markdown |

`latest.json` 指向最近一次，前端「评测」页读它。

**与上次基线对比**是报告的核心价值：哪条从绿变红、哪条从红变绿、
过程指标涨了还是跌了。

---

## 九、产物为什么在 `~/.keeper/evals/`

不放在代码目录，理由：

- 评测产物**体量大且频繁变化**，不该进版本库
- 它属于**运行数据**，与会话、记忆同级
- 代码目录要保持干净（打包时会被排除）

**基线也不进版本库**：基线依赖本机配置（模型、插件、工作区），
换台机器就没有可比性，进库只会误导。

```
~/.keeper/evals/
├── baselines/   基线（json = 真相源，md = 人看）
├── runs/        每次运行的明细
└── api-logs/    API 触发的运行日志
```

---

## 十、「能变红」的验收

评测本身也要验证：**故意改坏一处，基线必须变红**。

验证过两个方向：

1. 改坏断言（期望值改成错的）→ 对应用例变红
2. 改坏被测逻辑（比如关掉某个工具）→ 对应用例变红

两个方向都验过，才能确认评测不是「永远绿」。

---

## 十一、已知限制

- **只有 smoke 用例集**：用例数量少，覆盖有限
- **不做语义正确性判定**（L3 刻意不做）
- **串行执行**：用例多了会慢
- **基线不跨机可比**：依赖本机配置指纹
- **烧真钱**：每次运行都是真实的 LLM 调用
