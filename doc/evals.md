# 效果评估闭环（Evals）

> 本文描述**已实现**的评测闭环。落点：`keeper/evals/`（spec / asserts / harness /
> runner / report / run）、产物目录 `~/.keeper/evals/`。

---

## 一、一句话

用**固定的普通聊天用例**跑 agent，用**程序化断言**判定结果，
产出**可 diff 的基线**，让「改了之后变好还是变坏」有据可依。

---

## 二、为什么不依赖「agent 定位」

评测不假定 agent 是什么角色、有什么能力。用例是**普通聊天**：

```
问题：把这个函数改成支持批量输入
断言：工作区里出现了改动后的文件 / 输出里包含某些关键词 / 步数没超上限
```

好处：换 agent、换模型、换插件都能用同一套用例跑，结果可比。

---

## 三、三层判定（刻意只做前两层）

| 层 | 判定什么 | 怎么做 |
|---|---|---|
| **L1 能不能干完** | 任务是否完成 | 程序化断言 |
| **L2 干得好不好** | 过程指标（步数、token、成本、耗时） | 从 `llm_calls` 聚合 |
| L3 干得对不对 | 语义正确性 | **不做** |

L3 不做，因为要引入 LLM judge，而 judge 换个模型 / 换个提示词评分口径就变了，
历史基线全部作废。评测最怕的就是**口径会漂**——漂了就无法比较。

### 3.1 断言是纯程序化的

`evals/asserts.py`：不引入第二个模型。

断言类型大致包括：文件是否存在 / 内容是否含某串 / 步数上限 / token 上限 /
是否调用了某工具 / 是否产生了某产物。

---

## 四、隔离：三重（其中一条是可验证的断言）

评测最怕**污染真实数据**和**跑不起来**：

| 隔离 | 做法 |
|---|---|
| **独立数据库** | 用 SQLite backup API 把真实库复制一份到运行目录 |
| **独立进程** | 评测在独立进程里跑，不干扰主服务 |
| **独立工作空间** | 用的是**会话空间**（运行期唯一的工作目录），且会话空间的根被 `KEEPER_WORKSPACE_ROOT` 指到 `~/.keeper/evals/workspace`；「我的空间」也被重定向到评测自己的临时目录，被测 agent 碰不到用户真实的文件 |

工作空间这一条要特别小心：运行期的工作目录**早就从「用户空间」改成了会话空间**
（`chat_sessions.user_space_id` 是历史遗留列，运行期不读）。评测如果还按老模型把
setup 文件写到别处，agent 看到的目录永远是空的——十条用例会集体扑空，而报告里
全是「文件不存在」，看起来像模型不行，其实是评测自己接错了线。

同理，`read_only` 曾经是**假的**：运行期的 `resolve_workspace` 把它写死成
`False`，而评测却按用例声明 `allow_writes: false` 就以为工作区是只读的。
现在评测在进程内把它按用例覆盖上，「只读区不得写入」那条用例才真的测到了东西
（守卫的只读白名单会拦下 `cp`），而不是名义通过。

只读语义对 code 子 agent：**明确按可写处理**（产品决策，不是缺口）
--------------------------------------------------------------------
守卫（`tools/guard.py`）拦的是**工具调用**。它已经接到了子 agent 的工具桥
（`process.py` 的 `_delegate_bridge`）上，所以 code 沙箱里
`kt.call("bash__run", ...)` 也会被守卫过一遍。

但 code 沙箱本身**不是真沙箱**：它是「独立 venv + 一个运行目录」，跑的是**同权限
子进程**，`scan_code` 只是静态正则扫描。于是它写文件可以绕开一切——Python 自己
的 `open('/abs/path', 'w')` 没人管。

对此的判断是**威胁模型**，不是技术能力：
- 只读约束要防的是**第三方插件乱写用户文件**（插件代码不是模型写的，可能失控）。
- code 子 agent 跑的是**大模型自己刚写的代码**，风险来源是模型自己的意图，
  不是外部插件。所以产品上明确把 code 委派员标记为**可写**
  （`keeper/agent/delegatee.py` 的 `Delegatee.writable`，
  `code_delegatee.py` 里置 `True`），守卫对它按可写区处理。

注意这里只放开「能不能写工作区」，**没有**放开「能不能写到工作区外面」：
路径越界（extra_roots 之外）照样由守卫拦，委派桥和主链路走同一套检查。

评测侧对应地有一个显式开关：用例可以声明 `allow_delegatee_writes: true`，
表示「这条用例里 code 委派员写工作空间不算隔离失效」。理由同上——不采信
「谁写的」这种含糊判断会引入随机红（模型偶尔派子 agent、偶尔不派）。
声明这个开关之后，`read-only-write-refused` 真正测的是**主 agent 直接动手写**
会不会被守卫挡住、以及被拒后会不会谎称「写入成功」。

如果将来威胁模型变了（比如要允许模型装第三方插件并让它写文件），需要重新评估：
那时给 code 沙箱进程真正的 OS 级只读（容器 / 受限用户）才必要。

**进程隔离是前提，不是可选项**：agent 会写文件、会连 MCP，跑在主进程里一旦出错
影响的就不只是评测。

其中「独立数据库」是可验证的断言——评测结束后真实库应当**未被修改**。

## 五、配置指纹

没有配置指纹，基线就是一堆孤立数字：换了个模型、换了个插件，数字变了，
但你不知道是「改好了」还是「配置变了」。

所以每条基线记录当次运行的配置指纹（模型、插件、关键参数），
对比时**先比指纹**，指纹不同就直接提示「不可比」。

---

## 六、用例规格（`evals/spec.py`）

一条用例 = 一个问题 + 一份断言 + 若干准备条件。

刻意做得很薄：**只支持「确定性准备」**，不支持预置记忆 / 预置历史——
那两样要么依赖记忆抽取（模型侧，不稳定），要么让用例变成另一个要维护的系统。

用例文件 YAML，当前自带 `cases/smoke.yaml`（冒烟集）。

---

## 七、执行（`evals/runner.py`）

三条编排取舍：

1. **串行跑用例** —— 评测烧的是真钱（每条一次完整 ReAct），并发只会让失败率
   上升，不利于定位
2. **逐条判定后继续** —— 一条失败不影响其他条
3. **过程指标从 `llm_calls` 取** —— 与可观测同源，不另建统计

命令行：

```bash
# 跑默认 smoke 用例集（自动选库里第一个 active agent）
python -m keeper.evals.run
```

常用参数：

| 参数 | 作用 |
|---|---|
| `--agent <id>` | 指定被测 agent（不传则自动取库里第一个 active 的） |
| `--suite <name>` | 用例集（可重复；默认 `cases/` 下全部） |
| `--case <id>` | 只跑指定用例（可重复）——调试单条用，省得每次烧十几轮 token |
| `--run-id <id>` | 本次运行 id（默认时间戳） |
| `--case-timeout <秒>` | 单条用例墙钟上限 |
| `--baseline <run_id>` | 与指定基线对比 |
| `--no-compare` | 不与任何基线对比 |
| `--source-db <path>` | 被复制的源库路径（默认 `keeper/data/keeper.db`） |
| `--show <run_id\|latest>` | 只打印某份历史报告后退出 |
| `--compare-only <run_id>` | 把该历史报告与 latest 对比后退出 |
| `-v / --verbose` | 打开 debug 日志 |

产物根目录可用环境变量 `KEEPER_EVALS_DIR` 覆盖（默认 `~/.keeper/evals/`）。

## 八、报告（`evals/report.py`）

两层产物，职责不同：

| 产物 | 用途 |
|---|---|
| `baselines/<run_id>.json` | **唯一真相源**：机器读、前端读、对比读 |
| `baselines/<run_id>.md` | 人看的 Markdown |

`latest.json` 指向最近一次，前端「评测」页读它。

**与上次基线对比**是报告的核心价值：哪条从绿变红、哪条从红变绿、
过程指标涨了还是跌了。

---

## 九、产物为什么在 `~/.keeper/evals/`

不放在代码目录，理由：

- 评测产物**体量大且频繁变化**，不该进版本库
- 它属于**运行数据**，与会话、记忆同级
- 代码目录要保持干净（打包时会被排除）

**基线也不进版本库**：基线依赖本机配置（模型、插件、工作区），
换台机器就没有可比性，进库只会误导。

```
~/.keeper/evals/
├── baselines/   基线（json = 真相源，md = 人看）
├── runs/        每次运行的明细
└── api-logs/    API 触发的运行日志
```

---

## 十、「能变红」的验收

评测本身也要验证：**故意改坏一处，基线必须变红**。

验证过两个方向：

1. 改坏断言（期望值改成错的）→ 对应用例变红
2. 改坏被测逻辑（比如关掉某个工具）→ 对应用例变红

两个方向都验过，才能确认评测不是「永远绿」。

---

## 十一、已知限制

- **只有 smoke 用例集**：用例数量少，覆盖有限
- **不做语义正确性判定**（L3 刻意不做）
- **串行执行**：用例多了会慢
- **基线不跨机可比**：依赖本机配置指纹
- **烧真钱**：每次运行都是真实的 LLM 调用
