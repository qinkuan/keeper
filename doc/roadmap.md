# 路线图

> 本文是**未来要做的功能**，不是待办清单。
> 技术债、已知缺口这类「欠账」分散在各模块自己的文档里，见文末「相关文档」。

keeper 的定位是**本地知识库 agent**（读 → 找 → 改 → 交，并记住关于你的事）。
接下来的三个方向都围绕它展开——前两个补「我的空间」这个知识库本体，
第三个补「关于你的知识」：

| 方向 | 一句话 | 详情 |
|---|---|---|
| **① 我的空间：文件展示与编辑** | 让「我的空间」从「能看」变成「能改」——每种文件类型都有自己的展示与编辑方式 | [`user-space.md`](user-space.md) |
| **② 我的空间：向量跨模态搜索** | 给空间里的文件建索引，让 agent 能按**语义**找到它们，而不只是按文件名 | [`user-space.md`](user-space.md) |
| **③ 长期记忆库** | 记忆从「今天」跨到「永远」——长期事实 + 衰减 + 用户画像 | [`memory.md`](memory.md) |

## ① 我的空间：文件展示与编辑

### 现状

空间里的文件已经能**看**：

- Markdown / 纯文本 / 代码 / JSON·YAML·CSV —— Monaco 编辑器，可改可存
- Excel（xlsx/xls/csv/tsv）—— 表格预览，单元格可编辑，公式格式保留，能存回原文件；
  也可「用系统应用打开」看原样（图表 / 条件格式等预览不还原的东西）
- Word（docx/docm）—— **自研只读渲染**（2026-10 起，keeper/docx/ 解析 + web 的
  DocxViewer 画）：段落/表格/图片/编号/样式继承都还原，页面按 A4 版面呈现；
  浮动定位、SmartArt、公式、修订不还原（渲染器会明说，并给「用系统应用打开」兜底）
- PowerPoint（pptx/pptm）—— **不做页面预览**，只提供「用系统应用打开」
- PDF —— pdf.js 渲染、翻页
- 图片 —— 缩放平移
- Vega / Mermaid —— 渲染成图（.vg.json / .mmd）
- HTML / 视频 —— 交给浏览器
- 其余二进制 —— 只给下载

但「看」与「改」之间还有大片空白：**PDF 不能标注、图片不能改、音频没有转写、
视频没有字幕**。而 agent 与人的分工正在往「人改一半、agent 改一半」走。

Office 文档的页面内预览走过一段弯路（2026-10）：先有一版内容抽取（zip + XML 抽
文字/表格/图片），实测与本地应用差异大到「根本没法看」——OOXML 的版面信息远多于
文字，只抽文字的渲染上限就是「演示大纲」。后来找到出路：**不做 100% 还原，只做
「读得懂、读得舒服」的自研渲染**（keeper/docx/ 解析成 IR，前端按 IR 画）——
它不追求像素级一致，而是把版面的**语义**（标题层级、编号、表格网格、缩进对齐、
字体字号）如实还原，剩下还原不了的（浮动定位、图表、公式、修订）**显式列出来**
告诉用户，并给「用系统应用打开」这条 100% 保真的路兜底。

保真度更高的两条路仍然成立但没走：捆绑 LibreOffice 转 PDF（约 300MB）、上
OnlyOffice Document Server（同样 200MB+ 量级，且要处理许可）——都与这个项目的
轻量桌面定位冲突。真要 100% 保真，「用系统应用打开」本身就够了。

### Word 已进检索索引（2026-10）

docx 不只是"能看"，也**能被搜到**：

- 新切片器 `search/ingest/docx.py`：复用自研 docx 解析（`keeper/docx/`）拿标题层级，
  切法与 Markdown/PDF 同构（标题树 → 章节 → 叶子块），表格转 Markdown 表格文本。
- 标题层级有三个来源：`w:outlineLvl`（大纲级别，最准）→ 中文编号式标题
  （"第一编" / "第三章" / "第二节"——法律文书里这才是真结构）→ 标题样式名。
- **段落是 docx 的"页"**：`start_line`/`end_line` 存的是**块序号**（与前端渲染同序），
  搜索结果点进去能滚到准确的那一段并高亮。`locator` 留空——docx 没有页，
  硬塞"第 12 段"会被当成"第 12 页"。
- `source_kind="docx"` 让前端知道该怎么显示定位（"第 N 段" vs "第 N 行" vs "第 N 页"）。
- agent 侧读 docx 走既有的 `word__read` 工具（python-docx），不需要新工具。

### Word 渲染补齐 + @ 定位到段 + 受限回写（2026-10）

**① 表格边框 + 制表位（观感）**

- IR 加 `Table/TableCell.borders`（`w:tblBorders` / `w:tcBorders`）与 `Paragraph.tabs`
  （`w:tabs`）。边框解析会**合并表格级默认与单元格覆盖**：表格的 `insideH/insideV`
  在单元格上就是它的下边/右边；表格样式（"Table Grid"）里的边框也一并生效。
  以前所有表格一律画一圈灰框——**无边框表格现在不再有框**。
- 制表位按 `w:tabs` 还原：left / right / center 三种对齐 + 点/横线/下划线前导符。
  目录、条款对照表这类靠制表位对齐的排版不再歪。

**①.5 白纸居中 / 纸面宽度（踩坑记录）**

- 本项目关了 Tailwind preflight，全站 `box-sizing: content-box`——白纸那个
  `width: 页面宽` **不含页边距**，于是纸面被撑宽（左右页边距各加一次），
  文字区也跟着变宽，字排到纸外头；页面看起来"没在中间"。
  修法：白纸显式 `box-sizing: border-box`。
- 缩放层（`transform: scale`）改**绝对定位**：transform 不改布局，它 793px 的
  布局宽度会把外层撑出横向滚动条，外层一横向滚动，白纸就偏向一边甚至被裁掉。
  现在：占位盒（=缩放后的页面尺寸）负责滚动与居中，缩放层绝对定位贴左上角，
  占位盒 `overflow:hidden` 裁掉多余部分。实测左右留白各 12px，完全居中。

**①.6 预览区工具条合并到标题栏**

- 预览区自己那条工具条（文件名 + 缩放 + 「用 Word 打开」）撤掉了——它和
  「我的空间」标题栏那行重复了文件名（同一个名字前后各出现一遍）。
  现在**文件名只留标题栏一处**，缩放组（－ 适宽 ＋）和「用 Word 打开」
  都搬到标题栏右侧，和「添加到对话」同一行。
- 缩放状态仍在 DocxViewer 里（"适宽"要按预览区可视宽度实时算），
  靠 `DocxCtl` 句柄下命令 + `onInfo` 回报状态给标题栏。
- 「用系统应用打开」的文案跟着格式走：docx → 用 Word 打开，pptx → 用 PowerPoint 打开。

**② 大文档性能：实测后改了方向**

- 实测（民法典 2654 块 / 6557 个 DOM 节点）：一次性渲染约 380ms、滚动 60fps——
  **并不慢**。所以**没上虚拟滚动**（那会把"适宽缩放 + 占位高度 + 检索定位"三处
  都变成难点，收益不匹配风险）。
- 改成**分批渲染**：首屏 1200 块，其余每帧补 800 块，页面明说"正在渲染剩余 N 段"。
  跳转目标若还没画出来，等下一批补上后自动跳（`renderCount` 进 effect 依赖）。

**③ @ 检索命中 → 定位到段**

- `@` 菜单里的文件候选现在带着**命中落点**（docx=段序号 / pdf=页码 / md=行号）：
  副标题显示"…（第 2629 段）"，选中的 chip 上写"第 2629 段"。
- 新增 `web/src/lib/openFile.ts`（模块级「打开文件（带落点）」通道）：
  对话页点 chip → 切到「我的空间」并打开该文件、跳到命中段。
  对话页可能是整页（空间页没挂载），所以用"暂存 + 订阅"两段式，页面挂载后补做。
- 发给模型的话里也带上落点（"命中位置: 第 2629 段"），模型不用自己从头翻 2000 段。

**④ 受限回写（word__edit）**

- 插件新增 `word__edit`：**只动段落**（追加一段 / 替换某段纯文本 / 删掉某段），
  在原文件上做最小修改（保留样式、编号、图片、表格），**另存副本，绝不覆盖原件**
  （`out_path` 指回原文件会被直接拒绝）。
- 段号口径 = 正文里的第 N 个段落（1 起，不含表格内段落），与 `word__read` 一致。
- 明确不支持：表格内部、图片、页眉页脚、批注、修订——需要就说清楚，让用户在
  Word/WPS 里改。

### 要做的

| 方向 | 内容 |
|---|---|
| **文档族** | `.docx` / `.pptx` **只读预览**（标题层级 / 段落 / 表格 / 幻灯片列表）；Markdown → docx 导出 |
| **PDF 深加工** | 页面级批注、圈选高亮、裁页与合并、导出带批注的 PDF |
| **图片编辑** | 裁剪 / 旋转 / 标注（画框、箭头、文字），就地保存 |
| **音视频** | 音频转写（带时间戳）+ 波形；视频抽帧、字幕轨、关键片段 |
| **统一编辑协议** | 各种格式 → 统一的内部文档模型 → 回写原格式；让「在 agent 里改过的文件」与「在页面里改过的文件」是同一份 |
| **大文件** | 突破 2MB 预览上限：流式渲染、按需分页、虚拟滚动 |
| **版本与撤销** | 编辑历史、逐次撤销、恢复任意一版 |
| **diff 联动** | agent 改过的文件能像代码一样看 diff（现在只对 git 仓库内的文件有） |

### 为什么先做这个

「我的空间」是 agent 与用户共用的**唯一一块地盘**。它现在的定位是「给 agent 一个
安全的工作根」，往后应该长成「人和 agent 在同一批文件上协作的工作台」。
展示与编辑是这件事的地基——没有它，跨模态搜索索引出来的结果也没法就地打开改。

## ② 我的空间：向量跨模态搜索

### 现状

空间**已有检索层**（`search/`，原 k-search 迁入，见 [`indexing.md`](indexing.md)）：
Markdown / PDF 切片 → SQLite 存向量 + FTS5 关键词索引 → 混合检索（向量 + BM25 融合）。
它已经**接进 agent**（`kb.search` / `kb.read_pdf` / `kb.read_markdown`，见
[`kb-pdf-pages.md`](kb-pdf-pages.md)），也有独立的「搜索」页（索引管理 + 查询）。

剩下的缺口在**跨模态**：只覆盖文本类（Markdown / PDF），图片、代码、表格、音视频
都还没进索引。

记忆侧另有一套检索（jieba + SQLite FTS5），那是**关键词**匹配——
「那个讲缓存穿透的文档」搜不到标题叫「缓存那些事」的 md。

### 要做的

| 阶段 | 内容 | 状态 |
|---|---|---|
| **索引器** | 监听空间变更 → 分块 → 嵌入 → 写向量库；文件删除同步清向量 | ✅ 已有（增量索引，Markdown + PDF） |
| **分块策略** | 文本按语义段落切；代码按函数/类切；表格按行范围切；PDF 按页切（必要时 OCR）；图片整图；音视频先转写再按时间戳切 | 🟡 Markdown + PDF（PDF 走大纲标题树 + 页级切片，扫描件跳过） |
| **跨模态嵌入** | 文本走文本嵌入模型；图片走视觉嵌入（图文同向量空间）；表格与代码先转成带结构的文本再嵌；音视频走转写文本 | ⬜ 只有文本类 |
| **混合检索** | 向量 + FTS5 关键词 + 结构化过滤（路径 / 类型 / 大小 / 修改时间）→ RRF 融合排序 | 🟡 向量 + BM25 融合（自算 BM25F）；结构化过滤只支持路径前缀与文档类型 |
| **接入 agent** | 新增 `search` 工具（与记忆的 `recall` 并列，但搜的是**空间里的文件**）；`@我的空间` 的候选从「固定两项」变成「语义匹配出来的文件列表」 | 🟡 工具已接（`kb.search` / `kb.read_pdf` / `kb.read_markdown`）；`@我的空间` 候选仍固定两项 |
| **本地优先** | 嵌入默认走本地模型（不外传文件内容），API 嵌入作为可选 | ✅ 本地 LiteRT-LM；未装模型自动降级为纯关键词检索 |
| **成本控制** | 嵌入调用量、缓存（内容哈希 → 向量）、只索引白名单目录与大小上限、可暂停索引 | ✅ 内容哈希缓存、白名单目录、同步间隔可配 |

### 为什么先做这个

这是「我的空间」从**文件系统**变成**知识库**的一步。
有了它，agent 才能回答「我上次存的那个讲 XX 的 pdf 在哪」这类问题——
而这正是人愿意把文件放进一个工具里的理由。

技术选型上倾向于**纯本地**（`sqlite-vec` 或 `hnswlib` + 本地嵌入模型）：
文件内容不外传，也不需要维护一个向量数据库服务。

> 现状补充：已落地的是 **numpy 全量点积**（向量量级还小，不急着上 ANN）+ 本地
> LiteRT-LM 嵌入模型（`.litertlm`，模型文件在 `~/.keeper/search/models/`）。
> **没装 embedding 模型也能用**——关键词通道（FTS5/BM25）不依赖它，
> 索引与检索都会自动降级到纯关键词模式。

## ③ 长期记忆库

### 现状

记忆是**按会话作用域**的短期记忆（`~/.keeper/memory/sessions/<session_id>/turns.jsonl`
+ FTS5）：一个会话一份记忆，换个会话就换一套。没有跨会话的长期事实，也没有衰减。

### 要做的

| 层 | 内容 |
|---|---|
| **L1 短期** | 现有按会话记忆，保留 |
| **L2 长期事实** | 跨会话可复用的「事实」：人、项目、偏好、约定。带来源、置信度、时间戳 |
| **L3 用户画像** | 偏好、技术栈、习惯、常用路径；从事实里归纳出来，可被用户编辑 |
| **抽取** | 模型自主写（受控 schema）+ 系统侧候选抽取；两种口径都要有，因为只靠一边都不可靠 |
| **巩固与衰减** | 时间衰减权重；被反复提及的事实权重回升（间隔重复）；长期不被提及的淡出 |
| **检索** | 混合：向量 + 关键词 + 时间衰减权重；与 L1 短期记忆分层召回 |
| **冲突裁决** | 新事实与旧事实矛盾时怎么办（覆盖 / 并存 / 标记待确认） |
| **可见可改** | 用户能看、改、删自己的记忆；「忘掉这件事」是一个动作而不是改数据库 |
| **导出导入** | 记忆是用户资产，要能带走 |

### 为什么先做这个

「陪伴型」和「工具型」agent 的分水岭就在这里：工具型每次任务都该干净，
陪伴型需要**记得**。长期记忆库是 keeper 从「跑任务的 agent」变成「一直在的搭子」的
那块砖。

它也是 ② 的前提：没有长期事实，向量索引出来的也只是「一堆文件」，
而不是「关于你的知识」。
