### 1.1 工具并行：已实现但默认关

```184:186:keeper/config.py
    tool_parallel: int = 0
    ...
    tool_parallel_max: int = 5
```

档位：0 = 关闭（默认，行为与从前一致）/ 1 = 只读工具可并行 / 2 = 只读 + 显式声明可并行。

默认关是因为并行会让「工具调用顺序」变得不确定，而多数工具依赖前一步的结果。
要开的话在 `settings.yaml` 的 `context:` 段设 `tool_parallel: 1`。

## 二、未完成

### 2.1 记忆衰减与用户画像（原 P1-2）

**现状**：记忆是**会话级**的（`~/.keeper/sessions/<id>/turns.jsonl` + FTS5），
没有跨会话的长期事实库，也没有衰减机制。

要补的是：

- 长期事实的抽取与存储（跨会话可复用）
- 衰减（越久远的记忆权重越低）
- 用户画像（偏好、常用技术栈等）

**为什么还没做**：长期事实的写入口径很难定——模型自主写会不可控（见
`memory.md` 里对 MemGPT 式方案的否决理由），系统侧抽取又需要定义「什么算事实」。
当前优先做了会话级 + 检索，够用。

### 2.2 prompt dump 脱敏 + 危险工具二次确认（原 P2-2）

**现状**：代码里**没有**脱敏与二次确认的实现（已 grep 确认）。

- `observability/dump.py` 会把完整 prompt 落盘，含用户代码与可能的密钥
- 危险工具（如 bash）执行前没有二次确认弹窗

**风险**：本机使用问题不大；但若要给多人用或上服务器，这两项是硬缺口。

### 3.2 企业跨团队角色编排（原 `doc/collaboration-design.md`）

原设计了一套「部门内角色」模型：

| 角色 | 定位 | 职责 |
|---|---|---|
| **keeper** | 外交部 | 部门对外唯一窗口，收发跨部门消息，本地保存全部往来记录 |
| **planner** | 总参谋部 | 分解需求、组织内部资源、汇总方案、编排任务与发布顺序 |
| **worker** | 工程兵 | 只按任务改代码 + 自测 |
| **checker** | 质检 | 契约一致性、集成验证、代码评审 |

关键规则：**谁提出需求，谁的 planner 主导汇总**；worker 不需要知道跨部门的存在。

**现状：未实现。** 代码中没有 planner / worker / checker 的角色概念。

而且原设计写明「四类角色全部通过 **MCP** 交互」——这与当前采用的 **A2A**
协议路线冲突（见 `collaboration-contract.md`）。所以即便将来要实现，
也需要按 A2A 重新设计通道，不能直接照搬。

原文档已从项目根 `doc/` 移除（可从 git 历史恢复），要点保留在此。

## 五、优先级建议

按「风险 × 收益」排：

1. **危险工具二次确认**（安全缺口，且实现不复杂）
2. **连接池 + 永久错误重试**（直接影响稳定性与成本）
3. **只读开关可编辑**（配置灵活性，顺手可做）
4. **记忆长期事实**（收益大但设计难，建议先定口径再动手）
5. **对话分支**（锦上添花）
