# keeper 记忆与上下文工程设计

> 本文描述**已实现**的记忆机制。落点：`memory/`（retriever / store / extractor / tools）
> 与调用方 `chat/service.py`、`agent/process.py`。

原文档含大量方案调研（Context Engineering 四策略、MemGPT 对比等），因为决策已落地，
这里只保留**结论与依据**，调研过程不再重复。

---

## 一、要解决的问题

一次 `ask()` 里，模型看到的是「当前问题 + 最近若干轮」；跨会话的历史全在库里
但不会自动进上下文。表现是：

- 用户说「上次那个方案」→ 模型不知道指哪个
- 一轮里的第 8 步看不到第 1 步的完整输出（只有摘要）

要补的是**跨轮、跨会话的上下文连续性**，且不撑爆上下文窗口。

---

## 二、方案：三层

| 层 | 内容 | 落点 |
|---|---|---|
| **L1 短期记忆** | 本会话的逐轮记录（原文 + 块摘要），JSONL 存文件 + FTS5 索引 | `memory/store.py` |
| **L2 注入** | 最近 N 轮直接进 messages（角色交替，不塞 system） | `agent/process.py` |
| **L3 检索** | 需要更早的内容时，模型自己 `recall` / `read` 拉取 | `memory/tools.py` |

**不做**「agent 自主写记忆」（MemGPT 式）——见第四节决策记录。

### 2.1 L1：短期记忆的存储

目录（**按天**一份，同一天开的多个会话共享记忆）：

```
~/.keeper/memory/days/<YYYY-MM-DD>/
├── turns.jsonl        轮记录（原文，唯一事实来源）
└── index.db           FTS5 索引（纯派生数据，可随时重建）
```

- 落盘根目录可用环境变量 `KEEPER_MEMORY_DIR` 覆盖
- `turns.jsonl` 按 `message_id` **幂等覆盖**（同 id 只留最新版）
- 索引是**派生数据**，重建随时可做，因此不做迁移、只做 `reindex()`（`memory/store.py`）
- 写入是同步文件 IO（都很快），异步化由调用方决定

一轮记录包含：用户问题、助手回答、以及该轮的 **step 块**（供 `read` 惰性展开）。

### 2.2 L2：最近 N 轮直接注入

`agent/process.py` 取最近 N 轮的原文明细直接放进 messages。

**用 messages 角色交替，而不是塞进 system 段落**：system 里塞大段历史会让模型
分不清「指令」和「历史」，且难以做长度控制；messages 是模型训练时熟悉的形态。

### 2.3 L3：agentic retrieval（模型自己拉）

两个工具（`memory/tools.py`）：

| 工具 | 作用 |
|---|---|
| `recall(query)` | 检索，返回命中块的**摘要 + block_id**（不是全文） |
| `read(block_id)` | 惰性展开某个块的完整原文 |

两步式是刻意的：先让模型看摘要判断相关性，只对认为相关的块拉原文——
避免一次把大段无关内容倒进上下文。

## 三、检索：jieba 预分词 + SQLite FTS5

### 3.1 为什么必须在 Python 侧分词

FTS5 自带的 `unicode61` / `trigram` **都不做中文分词**。中文文本不分词直接入库，
等于按字切，检索「登录改 jwt」会命中一堆无关内容。

所以：**jieba 分词在 Python 侧做完，再喂给 `tokenize='unicode61'` 的 FTS5 表**。

```python
# memory/retriever.py
"USING fts5(doc_id UNINDEXED, content, tokenize='unicode61')"
```

两个细节：

- **单字 CJK token 一律剔除**——`unicode61` 不索引单字 CJK，留在查询里只会引入噪音
- **不用 jieba 自带停用词表**（上千词，过度）；只用一份精简停用词 + 支持 `add_user_word`
  加领域词

### 3.2 为什么现在不用向量库

- 本地单机，不希望引入额外进程 / 依赖
- 记忆规模是「一个用户的会话」，量级远不到需要 ANN
- FTS5 关键词检索**可解释**：命中什么词一目了然，排查相关性问题比重排向量容易

代价：语义相近但用词不同的召回不到。当前接受这个取舍。

> **这个取舍会变**：长期记忆库（见第八节）要做混合检索，向量是其中一路。
> 到时仍然倾向纯本地（`sqlite-vec` + 本地嵌入模型），理由同上——
> 不引额外服务、不外传内容。

### 3.3 索引失效检测

分词规则变了（比如加了停用词）会让旧索引与新查询不匹配。`MemoryIndex` 记一个
`_seg_version`，不匹配则 `is_stale()` 为真，触发重建——**靠原文在 JSONL 里，重建随时可做**。

## 四、关键决策记录

### 4.1 不做「agent 自主写记忆」（MemGPT 式）

否决理由：

1. **写入内容不可控**：模型会写它认为重要的，可能漏掉真正需要的
2. **额外 token 开销**：每轮多一次「写记忆」的 LLM 调用
3. **难以排错**：召回不准时，分不清是写坏了还是检索坏了

替代：**系统侧异步抽取**——一轮结束后由系统跑摘要（`memory/extractor.py`），
不占 ReAct 主循环、不额外要模型决策。

`extractor` 接受 duck-typed 的 `LLMChat`（只要有 `async def chat(messages, system)`），
与具体 LLM 实现解耦。

> **长期记忆库要重新审视这条决策**。第八节里 L2「长期事实」层采用
> **双通道**：系统侧抽候选 + 模型侧受控写入（带 schema 校验）。
> 纯系统侧抽不到「模型自己意识到的重要结论」；纯模型侧写不可控。
> 两边都要，且写入必须过 schema 与置信度门槛。

### 4.2 摘要是「块级」而非「轮级」

一轮里第 8 步看不到第 1 步的完整输出，是因为只存了轮级摘要。所以按 **step 块**
建立索引，`read(block_id)` 能精确展开某一步的原文。

---

## 五、注入位置与容量

- **位置**：messages 角色交替（`user` / `assistant`），不塞 system
- **最近 N 轮**：直接注入原文（L2）
- **更早**：靠 `recall` / `read`（L3），模型自己决定拉多少

这样上下文长度是**可控且按需增长**的，不会随着会话变长无限膨胀。

---

## 六、与可观测的关系

两者都要「记录」，但目的不同，不共用：

| | 记忆 | 可观测 |
|---|---|---|
| 目的 | 给模型补上下文 | 给人看开销与耗时 |
| 存储 | `~/.keeper/memory/days/<日期>/turns.jsonl` + FTS5 | `keeper.db` 的 `llm_calls` 等表 |
| 失败影响 | 上下文变短 | 主流程不受影响（try/except 兜住） |

---

## 七、已知限制

- **只做关键词检索**：语义相近但用词不同召回不到（长期记忆库会补上向量这一路）
- **无跨会话长期事实库**：记忆仍是**按天作用域**的
  （同一天开的多个会话共享记忆，换天即换记忆）——规划见第八节
- **摘要质量依赖模型**：抽取式摘要由 LLM 生成，偶有偏差
- **索引与原文可能不一致**：靠 `is_stale()` 检测 + `reindex()` 修复，不是实时同步

---

## 八、长期记忆库（规划，未实现）

> 总纲见 [`roadmap.md`](roadmap.md) 方向 ③。
> 本节是设计草案，**代码里还没有**。

### 8.1 为什么要做

现在的记忆是**按天**的：今天开的会话共享记忆，明天就换一套。
对一个「一直在的搭子」来说，这等于每天失忆一次——用户上周说过的
「我们用 pnpm 不用 npm」「数据库在 ~/dev/pg」都得重复交代。

长期记忆库要解决的是：**跨会话、跨天、可持续**地记住那些不会变的东西。

### 8.2 记忆的三个层次

注意这与第二节的「L1 短期 / L2 注入 / L3 检索」是**不同维度**——
那三层讲的是「一次 `ask()` 里上下文怎么来」，这里讲的是「记忆存在哪」。

| 层 | 内容 | 例子 | 生命周期 |
|---|---|---|---|
| **短期** | 现有按天记忆（逐轮原文 + 块摘要） | 「刚才那个命令怎么写的」 | 当天 |
| **长期事实** | 跨会话可复用的事实：人、项目、约定、偏好 | 「他用 pnpm」「这个库的生产库在 pg-prod-01」 | 长期，带衰减 |
| **用户画像** | 从事实里归纳出来的稳定特征 | 「偏好中文注释」「常用 Python 3.11」 | 长期，可被用户改 |

### 8.3 事实的数据模型

```json
{
  "id": "01M5...",
  "text": "这个项目用 pnpm，不用 npm",
  "type": "preference",              // fact | preference | project | relation | event
  "subject": "keeper",               // 事实的主体
  "object": "pnpm",                  // 客体（可选）
  "source_session_id": "01M5...",   // 从哪来
  "source_quote": "……原话……",       // 原文片段（可回溯）
  "confidence": 0.9,                 // 0–1
  "created_at": "2026-10-20T...",
  "last_recalled_at": "2026-10-22T...",   // 巩固用
  "recall_count": 4,                 // 被召回过几次
  "status": "active"                 // active | superseded | archived
}
```

`source_quote` 很关键：**没有原文出处的事实不可信**。它让用户能点开看
「你凭什么说我用 pnpm」，也能在事实出错时定位到是哪句话导致的。

### 8.4 抽取：双通道

| 通道 | 做法 | 问题 |
|---|---|---|
| **系统侧候选** | 一轮结束后异步跑抽取（复用 `memory/extractor.py` 的模式） | 抽不到「模型自己意识到的结论」 |
| **模型侧写入** | 给模型一个 `remember` 工具，schema 约束下写 | 不可控 —— 会写一堆垃圾 |

所以两个都要，但**模型侧写入必须过门槛**：

- schema 校验（类型、字段、长度）
- 与已有事实的相似度检查（近重复直接合并，不新建）
- 置信度低于阈值 → 只进候选池，不进正式库
- **每轮写入条数上限**（防模型刷屏）

`remember` 工具要不要进主循环，是个取舍：进则每轮多一次 token，
不进则模型不能主动记。倾向**不进**——用「轮后系统侧询问模型『这轮有没有值得长期记住的』」
代替，成本可控且不打断推理。

### 8.5 巩固与衰减

单纯的「越久远权重越低」不够用——重要的事会被时间埋掉。要两个机制：

| 机制 | 做法 |
|---|---|
| **时间衰减** | `weight = confidence * exp(-λ * 天数)`，λ 可配 |
| **间隔重复** | 事实被召回时 `recall_count += 1` 并刷新 `last_recalled_at`；反复被用的事实权重回升 |

两者叠加的效果：常用的事一直新鲜，冷门的事慢慢淡出——而不是靠「模型决定删」。

淡出**不删除**：标记为 `archived`，仍可检索到，只是不再优先召回。
真删除由用户做。

### 8.6 检索

长期事实的召回要**分层**：

```
用户问「上次那个 pnpm 的事」
   │
   ├─→ 短期记忆（今天的对话原文）    ← 关键词为主
   ├─→ 长期事实（按语义 + 衰减权重）  ← 向量 + 关键词 + 权重
   └─→ 用户画像（低频，命中即用）    ← 关键词
```

长期事实这一路的排序：`score = 相似度 * 权重`，权重含衰减与巩固。
与文件搜索（[`user-space.md`](user-space.md) 方向 ②）共用同一套嵌入模型与向量库，
避免维护两套。

### 8.7 冲突裁决

新旧事实矛盾时（新事实说「用 npm」，旧事实说「用 pnpm」），三种策略：

| 策略 | 行为 | 适用 |
|---|---|---|
| **覆盖** | 旧事实标 `superseded`，新事实生效 | 状态型事实（项目换了数据库） |
| **并存** | 两条都留着，靠召回时的权重与时间决胜 | 偏好型（可能只是这次例外） |
| **待确认** | 标 `pending`，召回时告诉模型「有两条冲突的事实」 | 影响大且无法自动判定的 |

默认策略：**偏好型并存、状态型覆盖**。类型由事实的 `type` 决定。

### 8.8 可见可改

记忆是**用户资产**，用户必须能：

- 列出全部长期事实（按时间 / 按权重 / 按类型筛选）
- 改写、删除单条
- 「忘掉这件事」——一个动作，不是改数据库
- 导出（JSON / Markdown）与导入

界面上放在设置弹窗里新增一段「记忆」，或独立页面。
这条不是可选项：**一个用户无法查看和纠正的系统，不该替他做决定**。

### 8.9 实施顺序

| 阶段 | 内容 | 理由 |
|---|---|---|
| **P1** | 事实表 + `remember` 工具 + schema 校验 + 候选池 | 先有存储与写入 |
| **P2** | 召回工具（`recall_facts`）+ 关键词检索 + 权重排序 | 先能用，再优化 |
| **P3** | 向量检索 + 与文件搜索共用嵌入 | 语义召回 |
| **P4** | 巩固 / 衰减 / 冲突裁决 | 记忆质量 |
| **P5** | 用户画像层 | 从事实归纳，可延后 |
| **P6** | 可见可改界面 + 导出导入 | 用户信任的前提 |

### 8.10 存储落点

| 数据 | 落点 | 理由 |
|---|---|---|
| 长期事实 | `keeper.db` 的新表 | 要 JOIN、要按状态查、要分页 → 关系库合适 |
| 事实的向量 | 与文件索引同一个向量库 | 共用模型与检索设施 |
| 抽取过程记录 | `memory/` 下的 JSONL | 与现有记忆文件风格一致，且是派生数据 |

长期事实**不是派生数据**——它是用户积累出来的资产，要备份、要导出，
所以进数据库（会被 `deploy.sh` 排除掉，但本机有 `.keeper` 目录的备份即可）。
