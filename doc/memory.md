# keeper 记忆与上下文工程设计

> 本文描述**已实现**的记忆机制。落点：`memory/`（retriever / store / extractor / tools）
> 与调用方 `chat/service.py`、`agent/process.py`。

原文档含大量方案调研（Context Engineering 四策略、MemGPT 对比等），因为决策已落地，
这里只保留**结论与依据**，调研过程不再重复。

---

## 一、要解决的问题

一次 `ask()` 里，模型看到的是「当前问题 + 最近若干轮」；跨会话的历史全在库里
但不会自动进上下文。表现是：

- 用户说「上次那个方案」→ 模型不知道指哪个
- 一轮里的第 8 步看不到第 1 步的完整输出（只有摘要）

要补的是**跨轮、跨会话的上下文连续性**，且不撑爆上下文窗口。

---

## 二、方案：三层

| 层 | 内容 | 落点 |
|---|---|---|
| **L1 短期记忆** | 本会话的逐轮记录（原文 + 块摘要），JSONL 存文件 + FTS5 索引 | `memory/store.py` |
| **L2 注入** | 最近 N 轮直接进 messages（角色交替，不塞 system） | `agent/process.py` |
| **L3 检索** | 需要更早的内容时，模型自己 `recall` / `read` 拉取 | `memory/tools.py` |

**不做**「agent 自主写记忆」（MemGPT 式）——见第四节决策记录。

### 2.1 L1：短期记忆的存储

目录（每个会话一份）：

```
~/.keeper/sessions/<session_id>/
├── turns.jsonl        轮记录（原文，唯一事实来源）
└── index.db           FTS5 索引（纯派生数据，可随时重建）
```

- `turns.jsonl` 按 `message_id` **幂等覆盖**（同 id 只留最新版）
- 索引是**派生数据**，重建随时可做，因此不做迁移、只做 `reindex()`
- 写入是同步文件 IO（都很快），异步化由调用方决定

一轮记录包含：用户问题、助手回答、以及该轮的 **step 块**（供 `read` 惰性展开）。

### 2.2 L2：最近 N 轮直接注入

`agent/process.py` 取最近 N 轮的原文明细直接放进 messages。

**用 messages 角色交替，而不是塞进 system 段落**：system 里塞大段历史会让模型
分不清「指令」和「历史」，且难以做长度控制；messages 是模型训练时熟悉的形态。

### 2.3 L3：agentic retrieval（模型自己拉）

两个工具（`memory/tools.py`）：

| 工具 | 作用 |
|---|---|
| `recall(query)` | 检索，返回命中块的**摘要 + block_id**（不是全文） |
| `read(block_id)` | 惰性展开某个块的完整原文 |

两步式是刻意的：先让模型看摘要判断相关性，只对认为相关的块拉原文——
避免一次把大段无关内容倒进上下文。

## 三、检索：jieba 预分词 + SQLite FTS5

### 3.1 为什么必须在 Python 侧分词

FTS5 自带的 `unicode61` / `trigram` **都不做中文分词**。中文文本不分词直接入库，
等于按字切，检索「登录改 jwt」会命中一堆无关内容。

所以：**jieba 分词在 Python 侧做完，再喂给 `tokenize='unicode61'` 的 FTS5 表**。

```python
# memory/retriever.py
"USING fts5(doc_id UNINDEXED, content, tokenize='unicode61')"
```

两个细节：

- **单字 CJK token 一律剔除**——`unicode61` 不索引单字 CJK，留在查询里只会引入噪音
- **不用 jieba 自带停用词表**（上千词，过度）；只用一份精简停用词 + 支持 `add_user_word`
  加领域词

### 3.2 为什么不用向量库

- 本地单机，不希望引入额外进程 / 依赖
- 记忆规模是「一个用户的会话」，量级远不到需要 ANN
- FTS5 关键词检索**可解释**：命中什么词一目了然，排查相关性问题比重排向量容易

代价：语义相近但用词不同的召回不到。当前接受这个取舍。

### 3.3 索引失效检测

分词规则变了（比如加了停用词）会让旧索引与新查询不匹配。`MemoryIndex` 记一个
`_seg_version`，不匹配则 `is_stale()` 为真，触发重建——**靠原文在 JSONL 里，重建随时可做**。

## 四、关键决策记录

### 4.1 不做「agent 自主写记忆」（MemGPT 式）

否决理由：

1. **写入内容不可控**：模型会写它认为重要的，可能漏掉真正需要的
2. **额外 token 开销**：每轮多一次「写记忆」的 LLM 调用
3. **难以排错**：召回不准时，分不清是写坏了还是检索坏了

替代：**系统侧异步抽取**——一轮结束后由系统跑摘要（`memory/extractor.py`），
不占 ReAct 主循环、不额外要模型决策。

`extractor` 接受 duck-typed 的 `LLMChat`（只要有 `async def chat(messages, system)`），
与具体 LLM 实现解耦。

### 4.2 摘要是「块级」而非「轮级」

一轮里第 8 步看不到第 1 步的完整输出，是因为只存了轮级摘要。所以按 **step 块**
建立索引，`read(block_id)` 能精确展开某一步的原文。

---

## 五、注入位置与容量

- **位置**：messages 角色交替（`user` / `assistant`），不塞 system
- **最近 N 轮**：直接注入原文（L2）
- **更早**：靠 `recall` / `read`（L3），模型自己决定拉多少

这样上下文长度是**可控且按需增长**的，不会随着会话变长无限膨胀。

---

## 六、与可观测的关系

两者都要「记录」，但目的不同，不共用：

| | 记忆 | 可观测 |
|---|---|---|
| 目的 | 给模型补上下文 | 给人看开销与耗时 |
| 存储 | `~/.keeper/sessions/*.jsonl` + FTS5 | `keeper.db` 的 `llm_calls` 等表 |
| 失败影响 | 上下文变短 | 主流程不受影响（try/except 兜住） |

---

## 七、已知限制

- **只做关键词检索**：语义相近但用词不同召回不到
- **无跨会话长期事实库**：L3「长期事实」层当前未实现，记忆仍是**会话级**的
- **摘要质量依赖模型**：抽取式摘要由 LLM 生成，偶有偏差
- **索引与原文可能不一致**：靠 `is_stale()` 检测 + `reindex()` 修复，不是实时同步
