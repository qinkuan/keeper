# 知识库读取：把本地资料交给 agent

本文档描述 keeper 怎么让 agent 读本地知识库 —— PDF 给**页面截图**，
Markdown 给**文本**。

实现位置：

- 渲染：`pdfpage/render.py`
- 工具：`knowledge/tools.py`
- 精确页码（切片侧）：`search/ingest/pdf.py`
- 精确页码（存储侧）：`search/store/db.py`
- 框架侧（工具结果带多模态块）：`tools/base.py` + `agent/process.py` + `llm/client.py`
- 回归脚本：`tests/test_kb_pdf.py`

---

## 一、第一原则：召回只定位，阅读才给内容

> **检索层回答「在哪儿」，读取工具回答「是什么」。**

| 阶段 | 输入 | 输出 |
| :--- | :--- | :--- |
| 召回 | 关键词 | 文件名 + **类型** + **位置** + 章节路径 |
| 阅读 | 路径 + 位置 | PDF 给**页面截图**，Markdown 给**文本** |

PDF 的文字层**只用来定位页码，不进 agent 的上下文**。

### 为什么不用文字

PDF 的文字层是「排版的副产品」：两栏排版左右交替、表格被拉平成一堆数字和竖线、
图里的文字根本不存在、连页码顺序都可能是乱的。模型读这样的文本**读不懂表格**，
也无法判断某个数字属于哪一行哪一列。

整页渲染则相反：页面上有什么就是什么，包括版式。

### 代价：只能定位，不能摘录

页图里的文字模型要自己「看」出来，偶尔会认错数字。这是纯图路线的固有代价，
不是实现问题。真出问题时可以在说明里补一行该页的文字层。

## 二、三个工具

### `kb.search(keyword)`

检索本地资料（PDF + Markdown 一起搜），**按命中内容的类型分别给**：

| 命中类型 | 给什么 |
| :--- | :--- |
| **Markdown** | 命中块 + 上下少量上下文（**纯文本**，约 60 行） |
| **PDF** | 命中处那 **3 页的截图**（第 N-1、N、N+1 页） |

两种形态会出现在同一次结果里。每条都标了**文件名、类型、位置**，并直接给出
**下一步该调哪个读取工具**（连参数都写好了，模型照抄即可）。

### `kb.read_pdf(path, start_page, end_page)`

按路径 + 页范围读 PDF，**一次最多 5 页**（超了报错，不静默截断）。

### `kb.read_markdown(path, start_line, lines)`

按路径 + 行号读 Markdown 的**文本**，默认 200 行，上限 600 行。

---

### 为什么要分成「搜」和「读」两个动作

PDF 与 Markdown 的内容形态根本不同：PDF 要给**图**（版面信息在图里，文字层
是排版的副产品），Markdown 给**文本**（它本来就是结构化文本，渲染成图只会
让模型更难读）。硬凑成一个形态只能两边都别扭，所以按类型各给各的。

而「召回」与「阅读」分开，还解决了另一个问题：**一次检索不该塞爆上下文**。
5 条 Markdown 命中各带 200 行 ≈ 2.4 万字符 —— 超过 `observation_limit`（3500）
就会被外部化，模型只拿得到一段预览，还得再 `read` 一次才看得全，一次检索
变成两三次往返。

于是有了这几条约束（都在 `knowledge/tools.py`）：

| 约束 | 值 | 为什么 |
| :--- | :--- | :--- |
| 一次最多给几条命中 | 5 | 更多只会稀释注意力 |
| **类型保底** | 每种类型至少留 1 条 | 召回是全局按分数排的，一条热门的 PDF 能把 5 个块全塞进 top_k，把 Markdown 命中整个挤掉——混合检索的意义正在于**跨载体** |
| PDF 最多附几组图 | 2 组（6 页） | 每页约 800~900 token，5 组就是 15 张图，上下文被图片吃光 |
| Markdown 窗口 | 60 行 | 命中块本身是**完整段落**，块外的行只是邻接内容；要细读自己调 `kb.read_markdown` |
| 文本总预算 | 5000 字符 | 见上（避免触发外部化） |
| 单条上限 | 1500 字符 | 别让一条吃掉全部预算 |
| 窗口去重 | 重叠 ≥60% 只给一次 | 同一章节的多个块展开后内容几乎一样，给 5 遍等于给 1 遍 |

### 门槛为什么是 0.65 / 0.3

BM25 的分数归一化后，**同一档的块会撞在同一个值**（实测 5 个不同的块都是
0.3423）。门槛定在档位之间，就会把一整类命中整体滤掉。0.65 落在两个档位
之间；宽松档 0.3 是因为实测 Markdown 块的典型分就是 0.3423。

### 「强 / 弱」不由分数决定

低置信度的命中只给命中块本身（不补足窗口），高置信度的给 60 行窗口。但
**判定依据是混合分 `score`，不是某个通道的分**——因为：

| 关键词 | kw 分 | vec 分 | 真实相关性 |
| :--- | :--- | :--- | :--- |
| 提示词工程 | 0.695 | 1.0 | 相关 |
| 上下文压缩 | 0.213 | 1.0 | 相关 |
| 外部化 | 0.334 | 0.792 | 相关 |
| **缓存穿透** | 0.318 | **0.833** | **完全无关** |

向量分**分不出相关性**（「缓存穿透」对「上下文治理」拿 0.833），关键词分也
有反例。所以「给多少」的判断权交给 **agent**——它看得懂标题路径与章节名，
一眼就知道哪条相关。我只负责标一句「这条大概不相关」，别让它浪费一次 read。

### 「有哪些文件」不单独做工具

列文件用现成的 **bash 插件**（`bin/bash-mcp`，`ls -1` / `ls -R`）就够，
不必再造一个 `kb.list_pdfs`。

但**路径抄写**是这一步最容易翻车的地方：中文文件名里常带空格与【】
（`08【考前2页纸】2026新大纲 基金私募~乐橙网.pdf`），模型从 `ls` 的输出里
手工复制时，漏空格、少一个字、多带一对引号都是常事。

所以 `kb.read_pdf` / `kb.read_markdown` 的 `path` 参数**故意做得宽容**
（`knowledge/tools.py:resolve_in_space`）：

| 传进来的 | 处理 |
| :--- | :--- |
| 精确相对路径 / 绝对路径 | 直接用 |
| 带了引号 `'x.pdf'` | 剥掉引号 |
| 只给文件名前缀 `08【考前2页纸】` | 在空间内模糊匹配，唯一命中就用 |
| **漏了空格** | 忽略所有空白后再比一次 |
| 完全对不上 | 报错 + 列出**名字最接近的 4 个** + 提示用 `ls` 再看一次 |

匹配到多个时**不替模型猜**——列出候选让它自己选（`00【新旧大纲变动对比】…`
在用户空间里有 4 个近似名，正是这种情形）。

## 三、渲染：pypdfium2

### 为什么不用 PyMuPDF

PyMuPDF 是 **AGPL**，会传染到整个产品，闭源桌面应用不能用。

`pypdfium2` 是 PDFium（Google）的 Python 绑定，**Apache-2.0 / BSD-3-Clause
双许可任选**，官方提供 macOS(x86_64/arm64) / Windows(32/64/ARM) / Linux
全平台预编译 wheel：

- 自带 PDFium 二进制，**不需要本地编译工具链**；
- Windows 上**不需要**额外安装 Microsoft VC++ 运行库（PDFium 用 `/MT` 静态链接了
  CRT）—— 这是 Windows 打包最常见的坑，实测扫过 `pdfium.dll` 的导入表确认过；
- macOS 侧要求 13+（wheel 标记 `macosx_13_0`）。

### 为什么不用 Pillow

`page.render()` 默认返回 PIL Image，那就要拖进 Pillow（又一个二进制依赖）。
它同时提供 `PdfBitmap.to_numpy()` → numpy 数组，keeper 已有 numpy →
PNG 编码自己写（zlib + 几十行，`pdfpage/render.py:encode_png`）。

### 分辨率

默认 `scale=2.0`（PDF 坐标基准 72 DPI，即 **144 DPI**），A4 → 1191×1684，PNG 约
300~800 KB。体积超 8 MB 时自动降一档倍率。

**实测（deepseek-flash）**：144 DPI 的整页图，模型能读出**正文小字**
（考题题干、页脚页码），不需要切半页，也不需要裁剪区域。

### 实测开销

| 动作 | 耗时 |
| :--- | :--- |
| 打开 PDF | ~0.01s |
| 渲染 1 页 | 0.05s ~ 1.1s（取决于页面复杂度） |
| 上传 1 页 | ~0.5s |
| 上传 3 页（并发） | ~1.0s |

图片 token：约 800~900 token / 页（厂商按缩放后的尺寸算）。

## 四、图片怎么进 agent 的上下文

### 走厂商 Files API，不走 base64 内联

选 Files API 的理由是**它是项目里已经跑通的通道**（`llm/files.py` 有完整的
multipart 上传 + file_id 引用实现），而 base64 内联要新增块类型、改发送层、
还要改上下文压缩（它按字符串处理 content）。复用现成通道改动面小得多。

代价：每页一次上传往返，且图片存在厂商侧（`expires_after` 未设 → 永久保存）。

### 框架侧改了什么

工具结果以前**只能是纯字符串**（`run` 的签名就是 `Awaitable[str]`），
图没有出口。现在：

1. `tools/base.py:ToolResult` —— 工具可以返回「文本 + 多模态块」。
   文本照旧走截断 / 外部化那套；**块不进文本预算**（图片按厂商自己的规则计费，
   被字符上限砍掉、或被「外部化成 block_id」就永远到不了模型眼前）。
2. `agent/process.py:_tool_message` —— 带块时 `content` 从字符串变成数组：
   `[{"type":"text",...}, {"type":"file","file_id":...}, ...]`。
3. `llm/client.py:_build_messages` —— tool 消息本来就转成 `HumanMessage`
   （role=user），所以「工具结果带图」在协议层就是「一条带图的用户消息」，
   与用户上传附件那条链路**完全同构**，厂商侧早就支持。
   `_has_file_blocks` 会识别它并走直连发送（绕开 langchain 对 file 块的形状改写）。
4. `agent/context_store.py` —— 带 `_media` 标记的消息**跳过外部化**：
   外部化会把 content 换成「文字 + block_id」，那是给文本用的机制，
   图片被这样处理一次就没了。

### 已知边界

- **挂起恢复**：图片不落库，恢复后模型只看到文字说明，需要重新调工具。
- **跨轮**：图片只在当次 ReAct 循环内有效（下一轮的历史里没有图）。
- **厂商门禁**：`llm/files.py` 只注册了 deepseek 的上传器。其他 provider 下
  `uploader_for()` 返回 `None` → 工具会明确报错「当前模型不支持文件上传」。

## 五、精确页码（这一步不做，后面全是错的页）

**问题**：以前 chunk 的 `locator` 是**章节页区间**，不是命中内容的精确页。
命中一个块却拿到「第 5-12 页」，按区间去渲染可能整页都不含命中内容 ——
agent 看着图编答案。

**做法**：`search/ingest/pdf.py` 的 `_join_pages` 额外返回每页在正文里的字符区间；
`_paragraphs_spans` 给每个段落带上它在原文里的字符区间；两者求交即得段落落在
哪几页 → 块 → `page_start` / `page_end`。

**代价为零**：只改 metadata，**正文一个字都没变** → `content_hash` 不变 →
旧向量全部复用，不重嵌不花钱。

> 前提是切片格式版本要对得上：新增了 `config.CHUNK_FORMAT_VERSION`，
> `chunks` 表加 `chunk_version` 列。它与 `EMBED_FORMAT_VERSION` **分开记**，
> 因为代价不同——切片版本变了只要重新切一遍（不花钱），嵌入版本变了要重新嵌入
> （花钱）。合进一列会让「要重嵌」和「只要重切」混为一谈。

## 六、⚠️ 扫描件无法被检索（当前最大的限制）

「我的空间」里的 PDF 绝大多数是**扫描件 / 图片型**，没有文字层。而召回靠的是
文字层 → 这些文件**一条都召不回来**。

- `search/ingest/pdf.py` 里 `total_text_len < _MIN_TEXT_CHARS` 的文件会被整个丢掉；
- 实测 16 个 PDF：只有 2 个能进索引（`简历` 与 `DeepSeek 内部研讨`），
  其余全是扫描件。

**所以当前的实际可用路径是 `kb.read_pdf` + `kb.list_pdfs`**（按路径和页码直接读），
`kb.search_pdf` 只对有文字层的 PDF 有效。

要让扫描件也能被召回，只有三条路：

1. **OCR**（文字层补齐）—— 代价高，但索引与召回逻辑完全不用改；
2. **按页存图 + 图片向量**（视觉检索）—— embedding 模型要能吃图片，litert-lm 不行；
3. **不动检索，改召回方式** —— 比如「先把整份 PDF 的页图给模型，让模型自己说要哪页」。

方案 1 最直接：OCR 之后现有的召回链路原样可用。
