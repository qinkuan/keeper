# 安全边界

> 本文记录 keeper 的**信任模型**、现有防护、以及**已知缺口**。
> 目的不是"说明我们很安全"，而是让人能自己判断：**哪些能信、哪些不能信、以及哪里还没堵上。**

---

## 一、当前形态：本机单用户

keeper 现在是**本机单用户应用**，没有入站认证：

| | 状态 |
|---|---|
| 入站 token / API Key | **已移除**（`auth/` 包整体删除） |
| 外部配置源（平台） | **已移除**（`plat/` 包整体删除，agent 全部本机创建） |
| 正式入口 | **桌面壳**（Electron） |
| 命令行形态 | 仅用于**演示**（`./start_keeper.sh`） |

**信任边界是「本机只有你一个人用 keeper」。**

这个假设成立时，内核不需要任何认证——它只监听回环地址，只有本机进程够得着。

---

## 二、威胁模型

内核里有**能让 agent 执行本机命令**的接口（bash 插件、文件读写、代码执行）。
它监听在一个本地 TCP 端口上。

删掉 token 之后，防护只剩两样：

| 防护 | 挡住了什么 | 挡不住什么 |
|---|---|---|
| **绑定回环**（`server.host: 127.0.0.1`） | 同网段的其它设备 | 本机的任何进程 |
| **CORS 白名单**（只放行本地 vite dev server） | 跨站 JS **读取**响应 | 跨站 JS **发起请求**（无自定义头时 GET 连预检都不触发） |

也就是说：

| 威胁主体 | 是否在防护范围内 |
|---|---|
| 同网段设备扫到端口 | ✅ 挡得住（回环绑定） |
| 用户打开的恶意网页 | ⚠️ **挡不住**——它能向 `127.0.0.1:<端口>` 发请求，只是读不到响应 |
| **用户本机的其他进程** | ❌ 挡不住——能直连端口 |
| 拿到内核进程的人 | ❌ 挡不住——能读数据库、读 `~/.keeper` |

**为什么网页挡不住**：浏览器同源策略拦的是"读别的源的响应"。一个恶意网页完全可以
`fetch("http://127.0.0.1:8080/agents/core/chat", {method:"POST", ...})` 把请求发出去，
只是拿不到返回内容。**CORS 只挡读，不挡发。** 以前挡它的是 token（网页猜不到入场券）。

### 🟡 这是移除认证的已知代价

| 项 | 说明 |
|---|---|
| **跨站请求可驱动内核** | 用户打开的任意网页都能向回环端口发起请求。接口形状是可知的——前端 JS 就同源托管在 `http://127.0.0.1:<端口>/`，恶意网页可以直接读它来研究 |
| **本机其它进程可驱动内核** | 同上，恶意程序能直接调接口 |
| 实际风险等级 | **取决于这台机器上有没有不可信代码**。个人开发机（只有自己的项目）风险低；装了来路不明的 npm 包 / 跑过不明脚本的机器风险高 |

**如果将来要恢复防护**，最省事的做法是把这个决策变成配置项而不是重新写一套：
在 `config.yaml` 加一个 `server.token`，非空时启用「`X-Keeper-Token` 头校验」，
前端从 `window.keeperHost.token` 读（preload 桥还在，删掉的那段可以很快加回来）。
`auth/api.py` 的原实现可从 git 历史取回。

### 建议的个人机器加固（不需要改代码）

- 内核只绑 `127.0.0.1`（默认就是，别改成 `0.0.0.0`）
- 不要在生产机 / 多人共用机上跑演示形态
- 演示形态用完就停（`./stop_keeper.sh`）

## 三、已移除的链路（历史说明）

早期版本曾有两条现在已经不存在的链路，留在这里是为了解释历史设计，
以及提醒：新增同类入口时必须把防护带回来。

### 3.1 平台对接（`plat/` 包）

曾经的形态：

```
keeperplatform (:9095)  ──token──▶  keeper 拉「我已添加」的 agent 定义
   agent 定义 / 插件资源              落库 → 下载资源 → 装配
```

对应代码（`plat/client.py` / `plat/sync.py` / `plat/fetcher.py`）已整体删除。
现在的等价物是**本地创建**（`POST /manage/agents`）——画像、插件绑定、模型绑定全在本机。

平台还带走了两个东西：

- **`config.yaml` 的 `platform.token`**（第三方凭据）——它随平台一起消失了。
  **如果你之前提交过 `config.yaml`，那个 token 已经泄露过**，建议去平台侧确认/轮换。
- **市场页**（`AgentMarketPage`）——没有外部来源，就没有市场。

### 3.2 凭据进版本库（**已随平台移除而消失，但历史泄露需处理**）

`config.yaml` 曾被 git 跟踪，其中 `server.auth.token` 与 `platform.token` 都是明文。

现在这两个字段都**已删除**（平台整体移除、认证整体移除），代码里不再有任何地方
读它们——但**已经泄露过的凭据不会因为代码删了就失效**：

- **`platform.token`** 是第三方凭据 → **需要去平台侧确认 / 轮换**（它不在代码里了，
  但仍可能有效）。
- **`server.auth.token`** 只影响本机回环，且认证已整体移除，失效即可。

另外：`config.yaml` **仍在 git 跟踪**。它现在没有敏感内容，但以后若再加凭据字段，
先把它移出跟踪（加 `.gitignore` + 改用不提交的 `config.local.yaml`）。

### 3.3 浏览器扩展 / 浮球

早期版本有一套「浏览器扩展 / 浮球」链路：扩展连内核走
`ws://127.0.0.1:<port>/agent-bridge`，握手校验 token 与扩展 `Origin`。

**这套链路现在已不存在**（内核里没有 WS 路由，没有 `browser/` 包）。
保留这段说明是为了提醒：新增 WebSocket 入口时，那两条校验（token + Origin）必须一起带回来。

## 四、插件是第三方代码

插件（`~/.keeper/plugins`）是**你本机上的第三方代码**，它通过 MCP / bin 子进程拿到
接近 shell 的能力。装插件前请确认来源：

- 插件走**子进程**而不是 import——但子进程同样能读写 `~/.keeper`、能调网络
- 仓库根的 `plugins/` 只是**参考副本**，运行时读的是 `~/.keeper/plugins`
- 装了插件等于在本机装了它的全部权限

`tools/guard.py` 提供**工作区路径越界**拦截（可写工作区只查路径越界），
但它管的是「agent 别写到不该写的地方」，**不是**「插件别做坏事」。

---

## 五、框架运行时的自举

`~/.keeper/framework/` 下集中管理的 python / node 运行时，是**下载来的可执行文件**。
它来自 `config.yaml` 的 `framework` 段（镜像地址 / 版本）。

这是本机信任边界里唯一的「外部来物」：信任它 = 信任那个镜像源。
自举时下载的包会做 SHA256 校验（见 `framework/` 内的下载与校验实现），
但**校验的是完整性，不是来源可信度**。

---

## 六、桌面形态的凭据取舍（记录用）

桌面壳曾经每次启动现生成 token，通过环境变量 `KEEPER_TOKEN` 交给内核。
这个取舍**不要为了方便改掉**——随机的才安全，写进 `config.yaml` 的迟早会被提交进仓库。

现在 token 整体移除了，桌面壳不再生成、也不再注入。理由是形态变了：
keeper 现在是**纯本机单用户**应用，正式入口只有一个，没有多端访问的需求。
代价见第二节。
