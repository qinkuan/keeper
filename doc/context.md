# 上下文治理：外部化 + 自动压缩

> 本文描述**已实现**的上下文治理。落点：`config.py` 的 `ContextSection`、
> `agent/context_store.py`、`agent/process.py`。

配套：`capability-loading.md`（减少进上下文的量）、`memory.md`（检索与取回）。

---

## 一、要解决的问题

ReAct 每步把 `THOUGHT` / `ACTION` / `OBSERVATION` **全量累加**进 messages。
长任务下输入 token 线性膨胀，直到撞窗口。

两个手段，都是为了**在中途把上下文压下来**：

| 手段 | 做什么 |
|---|---|
| **外部化**（externalize） | 工具输出超阈值就写盘，上下文里只留「首尾预览 + block_id」 |
| **压缩**（compact） | 输入 token 到水位时，把最早的一批步骤压成「骨架 + block_id」 |

外部化有**两条触发路径**，阈值各管一条：

| 路径 | 触发条件 | 阈值 |
|---|---|---|
| 单条超长 | 结果超过硬截断线 | `observation_limit`（3500） |
| 滚动外部化 | 已退出保活窗口 | `externalize_min_chars`（5000） |

**顺序必须是「先外部化、再截断」**：硬截断砍掉的中段既没落盘也没有 `block_id`，
模型永远拿不回来，只看到「省略了多少字符」；而内置工具（`fs.read_file` /
`fs.search_files`）都没有 `offset`/`limit` 参数，它只能原样重调同一个工具，
于是打转。外部化只多一步 `read(block_id)`，信息不丢。

反过来（先截断、再让滚动外部化判断）会让外部化**形同虚设**：messages 里的内容
已经 ≤ 3500，永远够不到 5000 那条线。

## 二、分层

| 层 | 内容 | 位置 |
|---|---|---|
| **L0** | 当前几步的完整输出（模型下一步要用） | messages，原文 |
| **L1** | 退出保活窗口后外部化的块 | 磁盘（`~/.keeper/context-store`），上下文里只留引用 |
| **L2** | 被压缩掉的历史步骤 | 磁盘，上下文里只留骨架 |

取回统一用 `read(block_id)`（`memory/tools.py` 的 `read` 也能读这些块）。

---

## 三、外部化的触发条件

两个阈值各管一条路，别把它们混成一个：

| | 字段 | 默认 | 管什么 |
|---|---|---|---|
| 内联上限 | `observation_limit` | 3500 | **单条超长**：超过就换成引用 |
| 滚动阈值 | `externalize_min_chars` | 5000 | **退出保活窗口后**：超过才换成引用 |

### 3.1 单条超长（`Process._fit_observation`）

> **长度 > `observation_limit`（3500）就外部化**

这条是**兜底之前的那一步**：超长结果的中间段没有 `block_id` 就等于丢了，所以
超过内联上限的都先写盘、换成「预览 + block_id」，模型 `read` 一下就能拿回全文。

注意「内联上限」这个叫法：它现在的含义不是「砍到多少」，而是「超过多少就不进
上下文」。调小它**不等于更省**——模型随后要把整块 `read` 回来，净 token 反而
上升（外加一次 LLM 往返）。按「多大的结果模型不会读完」来定，别按「省 token」。

```
工具返回 → 长度 > observation_limit → 写盘，上下文里换成「预览 + block_id」
                                 → 失败/豁免 → 才落到硬截断
```

### 3.2 滚动外部化（`Compactor.rolling_externalize`）

> **「已退出保活窗口」且「长度 > `externalize_min_chars`」**

**没有「刚返回就压」这条路**——模型下一步要用这份结果，换预览会漏内容。

```
工具返回 → 进 L0（原文，完整）
        → 走出保活窗口 且 长度 > externalize_min_chars
        → 写盘，上下文里换成「预览 + block_id」
```

硬截断（`observation_limit`）是外部化没触发时的**兜底**：总开关关掉、工具在
`never_externalize` 名单里、或写盘失败，才只剩它。它的文案里带「怎么缩小范围
重试」的指引——因为砍掉的中段没有 id 可读，模型需要知道下一步该干什么。

### 3.1 阈值为什么默认 5000

外部化会**改写中段消息，同样破坏前缀缓存**。实测 2000 字符就换引用时，
省下的 token 远抵不上后续缓存失效的代价。

## 四、压缩的触发

| 参数 | 默认 | 说明 |
|---|---|---|
| `compact_enabled` | `True` | 总开关 |
| `model_context_limit` | 64000 | 模型窗口（token），用于算水位 |
| `compact_ratio` | 0.7 | 用到窗口的这个比例就压 |
| `compact_min_steps` | 20 | 步数线（**且**要过水位下限） |
| `chars_per_token` | 2.5 | token 粗估（中文≈1.5，英文≈4），只用于算水位 |

### 4.1 步数触发为什么要带水位下限

实测：23k token（窗口 36%）时压缩，缓存命中率从 97% 掉到 68%，
**每步输入成本反而贵 13%**——省掉的多是命中价的便宜 token，却把后续一批
变成未命中价。

所以步数触发要**同时**满足水位下限（默认 0.7 倍真水位），不是光看步数。

## 五、配置项一览（`settings.yaml` 的 `context:` 段）

| 参数 | 默认 | 作用 |
|---|---|---|
| `enabled` | `True` | 总开关 |
| `externalize_min_chars` | 5000 | **滚动**外部化阈值（0 = 不做滚动外部化） |
| `never_externalize` | 空 | 豁免名单（填了的工具永不外部化，两条路径都不生效） |
| `retain_days` | 7 | 外部化块保留天数（0 = 不清理） |
| `observation_limit` | 3500 | **内联上限**：超过就外部化成引用，也是外部化不可用时硬截断的兜底上限 |
| `max_steps` | 30 | 一轮最多步数 |
| `read_budget` | 6000 | `read` 展开多块的总字符预算 |
| `max_ctx_recall` | 5 | `recall` 返回本轮外部化块的上限 |
| `pin_recent_reads` | 2 | 追回的内容保活几条 |
| `preview_head` / `preview_tail` | 400 / 200 | 留在上下文的首尾字符数 |
| `dir` | `~/.keeper/context-store` | 块存储目录 |
| `compact_*` | 见上 | 压缩相关 |
| `max_output_tokens` | 16384 | 单次 LLM 输出上限 |

### 5.1 `max_output_tokens` 为什么要显式设

ReAct 的 `ACTION_INPUT` 里常塞着整份文件，一次输出上万字符容易撞 provider 的
**输出上限而被静默截断**——表现是参数 JSON 不完整、工具莫名失败，而模型自己
完全不知情（它那边只是"输出结束了"）。

默认 16384 的由来：不少 provider（DeepSeek 的 deepseek-chat 就是）**默认
max_tokens 只有 4096**——"什么都不配"其实已经在被截了。16384 是它的 4 倍，
且提示词会把这个数字告诉模型，让它按预算分段输出。

### 5.2 `retain_days` 必须回收

外部化持续产块，且「先外部化、后又被压缩打包」会留下不再被引用的旧块，
没有回收磁盘会一路涨。

## 六、为什么不是「每来一条就压上一条」

三个理由：

1. 模型下一步要用这份结果，立刻换预览会漏内容
2. 每压一次就改写一次中段消息，**每改写一次就打散一次前缀缓存**
3. 外部化和压缩都会破坏缓存，触发越频繁越亏

所以滚动外部化是**退出保活窗口后**才压，且阈值取 5000 而不是更小。

（单条超长是例外：那条不看保活窗口，因为它不做「瘦身」而是**止损**——超限时
硬截断会把中段永久丢掉，换成「预览 + block_id」反而是信息不丢的降级。）

---

## 六之二、已知的一处内在矛盾（已修）

外部化原本排在硬截断**之后**：先把结果截到 3500，再让滚动外部化去判断要不要换成
引用。可 messages 里的内容已经 ≤ 3500，永远够不到 `externalize_min_chars` 的 5000
——外部化这条兜底路径在默认配置下**一次都没触发过**。于是「单条过大」只剩截断，
模型拿不到中段，也没有 id 可 `read`。

修法（`agent/process.py: _fit_observation`）：

```
先 externalize(min_chars=observation_limit)  → 给 block_id，模型能 read 回来
  └ 没触发（关掉 / 豁免 / 写盘失败）→ clip_observation 兜底
```

单条超长那条路径**用自己的阈值**（`observation_limit`）而不是复用
`externalize_min_chars`，正是为了不留下「3500~5000 既不外部化又被截断」的死角。

## 七、与记忆的关系

| | 上下文治理 | 记忆 |
|---|---|---|
| 方向 | 把**当前轮**的内容挪出去 | 把**历史轮**的内容取回来 |
| 存储 | `~/.keeper/context-store` | `~/.keeper/sessions/*.jsonl` + FTS5 |
| 触发 | 系统侧自动（水位 / 窗口） | 模型主动 `recall` / `read` |

两者共用 `read(block_id)` 的取回方式，但**块来自不同目录**。

---

## 八、已知限制

- **`chars_per_token` 是粗估**：中文 1.5 / 英文 4，混排文本的水位判断会有偏差
- **压缩不可逆**：压成骨架后原文只在磁盘里，模型要用得再 `read` 回来
- **`pin_recent_reads` 调参敏感**：保太少会「读了 → 被压 → 又读」抖动；
  保太多则上下文重新膨胀
- **压缩本身要消耗一次 LLM**：这是成本，不是免费的
